# 예매확정/취소 알림 파이프라인 — SQS → Lambda → SES 채택, SNS·EventBridge Scheduler는 보류

> 이 문서는 팀원이 공유한 아키텍처 노트("예매확정 알림 파이프라인: SQS·Lambda·SES", 2026-08-11 최초 작성/2026-08-12 갱신)의 설계 근거를 위키로 옮긴 것이다. 단, 그 노트가 제안한 **레포 분리(Lambda 전용 신규 레포)와 Infra `05_messaging` 신규 root는 참고만 하고 따르지 않았다** — 실제 구현은 [[2026-08-12-messaging-infra-placement]]대로 `04_data`+`03_registry`에 통합, Lambda 코드도 `modules/messaging/lambda-src/` 안에 둠. 이 문서는 그 구조 결정이 아니라, **"왜 SQS→Lambda→SES라는 파이프라인 자체를 골랐는가"**만 다룬다.

## 배경

예매확정/취소 시 이메일을 보내야 하는데, 이걸 예매확정 API 요청·응답 흐름 안에서 동기로 처리할지, 비동기로 분리할지, 분리한다면 어떤 조합(큐/토픽/스케줄러)으로 할지를 결정해야 했다.

## 결정

**SQS(대기열) → Lambda(소비·처리) → SES(발신)** 파이프라인을 채택한다. EventBridge Scheduler는 지금 요구사항에 없으므로 보류.

```
백엔드(예매확정 API) → SQS → Lambda → SES → 실제 메일함
```

## 왜 동기 직접 호출이 아니라 비동기 파이프라인인가

예매확정 API가 이메일 발송까지 동기로 처리하면 SES 호출 지연·실패가 그대로 사용자 응답 속도에 영향을 준다. 메일 발송은 예매 성공/실패를 좌우하는 핵심 로직이 아니므로, API 응답과 발송 처리를 분리하는 게 먼저 전제됐다.

## 왜 "Lambda 직접 비동기 호출"이 아니라 "SQS를 낀 Lambda"인가

Lambda를 백엔드가 비동기로 직접 호출해도 "기다리지 않고 응답"이라는 목적은 달성된다. SQS를 낀 이유는 그 이상 — **장애 상황에서의 안정성**:

| 이유 | 내용 |
|---|---|
| 재시도/유실 방지 | SES 호출이 일시 오류로 실패해도 메시지가 큐에 남아 재시도됨. 직접 호출이었다면 재시도 로직을 백엔드/Lambda가 직접 구현해야 함. 계속 실패하면 DLQ로 격리되어 원인 추적 가능 |
| 트래픽 버퍼링 | 인기 공연 오픈 시점처럼 예매가 몰려도 큐가 완충 역할을 해 Lambda가 처리 가능한 속도로 순차 소비 — 백엔드 API가 부하를 직접 떠안지 않음 |
| 응답 속도/발송 처리 분리 | 예매확정 API는 큐에 메시지만 넣고 즉시 응답 — 메일 발송 지연·실패가 사용자가 느끼는 응답 속도에 영향을 주지 않음 |

## 왜 SNS가 아니라 SQS인가

지금 이 이벤트(예매확정/취소)를 소비하는 곳이 **Lambda(SES 발송) 하나뿐** — SNS의 핵심 가치인 fan-out(다중 구독자 동시 전달)이 필요한 상황이 아니다.

| 기준 | SQS | SNS |
|---|---|---|
| 전달 방식 | Pull — 소비자가 처리 가능한 만큼 꺼내감 | Push — 도착 즉시 구독자에게 바로 전달 시도 |
| 구독자 수 | 단일 소비자에 적합 | 다중 구독자 동시 전달(fan-out)에 특화 |
| 실패 시 처리 | 큐에 메시지 보존 → 재시도 → DLQ 격리 | 제한된 횟수만 재시도, SQS만큼 유연한 보존 어려움 |
| 지금 구조와의 관계 | **채택** — 소비자가 Lambda 하나뿐 | 이메일 외 SMS·로그 적재 등 추가 구독자가 생기면 SQS **앞단**에 추가 검토 |

## 왜 Lambda인가 (SQS 소비자로서)

이벤트가 예매 확정/취소 시점에만 간헐적으로 발생하는 워크로드라, 상시 떠있는 컨슈머 서비스보다 이벤트 발생 시에만 실행되고 그만큼만 비용이 청구되는 서버리스가 자연스럽게 맞는다. `aws_lambda_event_source_mapping`(SQS 트리거)로 큐 폴링·오토스케일까지 관리형으로 처리되므로 별도 워커 프로세스를 운영할 필요가 없다.

## 왜 EventBridge Scheduler는 보류인가

Scheduler는 "특정 시점에 자동 실행"이 필요할 때만 의미가 있다. 지금 확정된 요구사항(예매확정/취소 알림)은 사용자 액션 즉시 트리거되므로 SQS+Lambda+SES만으로 충분하다.

공연 하루 전 리마인더 메일, 결제 대기 자동 만료처럼 **미래 시점에 트리거돼야 하는 기능이 요구사항으로 확정되는 순간** Scheduler → Lambda 트리거를 추가하면 된다. 그전까지는 만들어도 쓰이지 않는 리소스가 된다.

> ⚠️ 미해결: 원본 아키텍처 노트에 "EventBridge Scheduler를 이미 만든 팀원이 있다"는 메모가 있었다 — 실제 용도(리마인더 등)를 그 팀원에게 확인해서, 확정된 요구사항이 없다면 정리 대상인지 판단 필요.

## 고려한 대안

- **SNS(파이프라인 전체를 SNS 기반으로)** — 기각. 위 표 참고, 지금은 단일 소비자라 fan-out 이득이 없고 SQS의 재시도/DLQ 보존이 더 적합. 소비자가 여러 개로 늘어나면 SNS를 SQS 앞단에 추가하는 확장 경로(SNS→여러 SQS)를 재검토.
- **EventBridge Scheduler를 지금 같이 구축** — 기각. 시간 기반 트리거 요구사항이 아직 확정 안 됨, 미리 만들면 쓰이지 않는 리소스.
- **비동기 자체를 안 하고 동기 처리** — 기각. API 응답 속도가 외부 서비스(SES) 상태에 종속되는 걸 원치 않음.
