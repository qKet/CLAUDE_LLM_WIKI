# 대기열 적용 범위 — 지금은 "예매하기" 클릭 이후만

## 배경

[[../troubleshooting/loadtest-10000-open-run-cascading-failures]] 부하테스트로 확인한 사실: 지금 대기열(`QueueModal`, `BookButton.tsx`)은 사용자가 **"예매하기" 버튼을 누른 시점부터만** 작동함.

```
홈(/)  →  로그인  →  공연 상세(/events/[id])  →  [예매하기 클릭] → 대기열 → 좌석선택 → 예매
└──────────── 대기열 보호 안 됨 ────────────┘   └──────── 대기열 보호됨 ────────────┘
```

부하테스트에서 가장 먼저·가장 심하게 무너진 건 예매 단계가 아니라 **홈페이지 접속 자체**(성공률 10%) — 즉 지금 가장 취약한 구간이 정확히 대기열 사각지대에 있다는 게 실측으로 드러남. "이거 문제 아닌가?"라는 질문에서 시작된 논의.

## 결정

**지금은 대기열 적용 범위를 확장하지 않는다.** "예매하기 클릭 이후"라는 현재 범위를 그대로 유지하고, 대신:

1. [qKet/frontend#27](https://github.com/qKet/frontend/issues/27)(SSR 캐싱), [#28](https://github.com/qKet/frontend/issues/28)(frontend 헬스체크 분리), [qKet/backend#29](https://github.com/qKet/backend/issues/29)(backend 헬스체크 포트 분리) — 이 3건으로 홈/상세 구간의 붕괴 자체를 완화한다.
2. 대기열을 홈/상세까지 앞당기는 확장(실제 대형 티켓 사이트들이 오픈 시각에 사이트 진입 자체를 가상 대기실로 막는 방식)은 **지금 하지 않는다.**

## 이유

- 현재 프로젝트 규모(4인 팀, 포트폴리오/사이드 프로젝트)에서 진짜 대형 티켓 사이트급 동시접속을 상정할 필요가 크지 않다고 판단
- 위 3건(캐싱 + 헬스체크 분리)만으로도 오늘 재현된 수준의 붕괴(ALB 헬스체크 연쇄 장애, HealthyHostCount=0)는 상당 부분 막을 수 있을 것으로 예상 — "완전 무결점"은 아니지만 지금 리스크 대비 투자로는 충분하다고 판단
- 대기열 범위를 홈까지 넓히는 건 설계 변경 폭이 큼(모든 페이지 진입에 대기열 게이트를 걸어야 함, UX 전체에 영향) — 지금 당장 결정할 필요 없는 종류의 문제로 판단해서 보류

## 고려한 대안

- **A. 대기열을 사이트 진입(홈) 시점까지 확장** — 근본적으로 가장 강력하지만, 설계 변경 범위가 크고 UX 전체에 영향. 기각(지금은).
- **B. (채택) 현재 범위 유지 + 캐싱/헬스체크 분리로 완화** — 변경 범위가 작고, 위 부하테스트에서 발견된 구체적 원인(캐싱 없음, 헬스체크 스레드풀 공유)에 직접 대응하는 방식.

## 트레이드오프 / 남은 리스크

- 캐싱+헬스체크 분리를 다 적용해도, 홈/상세는 여전히 대기열 없이 로그인 인증 뒤에 그대로 노출됨 — 캐싱이 커버 못 하는 규모(오늘 테스트한 만 명보다 훨씬 큰 동접)가 실제로 온다면 다시 무너질 수 있음
- **재검토 트리거**: 실제 서비스 트래픽이 지금 상정한 규모를 크게 넘어설 조짐이 보이면(팀 논의 필요), 그때 대안 A를 다시 꺼내서 검토하기로 함
